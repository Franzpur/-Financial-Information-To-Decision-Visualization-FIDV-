内阁深度读本（重写版） · 2026-10-15 · 架构与产品判断（非令） · 供业主 Purkniv 审阅

业主原话：「我给你三种目标交互方式，你思考一下能否实现，你有什么看法，是否接入大模型会有利于实现，接入大模型会不会导致整个工程混乱和需要重塑。一、简单自然语言指令；二、表类数据输入；三、手动制图操作。」

0. 总纲：三种交互不是三套系统，而是同一状态机的三个输入面

在姊妹篇《交互性与自主作图》中，内阁论证了 SFC 从「静态展厅」迈向「自主制图台」的核心枢纽：在严格锁死三维坐标语法（1 类坐标 (s, x, y)、2 类坐标 ringCos/ringSin、3 类坐标 legalEntityCoord 及四项几何原语）的前提下，后端 BE-BUNDLE 只需引入一层声明式的图方案规约（ChartSpec）与原子操作集（ChartOps），即可扩展出单中心上下游链、多跳级联链、债务到期墙、同业集中度对标等丰富的图种。

站在这个架构基点上审视业主提出的三种目标交互方式，内阁的首要结论是：这三种方式完全可以实现，而且它们在工程上绝不能写成三条各自直通 Three.js 的独立管线，而必须收敛为修改同一份 ChartSpec 的三个前端/后端适配器（Three Surfaces, One State Machine）：

因为三者汇入同一个 ChartSpec，研究员在实际工作流中可以无缝混用三种方式：先粘贴一张从 Bloomberg 导出的 20 行供应链或债券到期表（方式二，瞬间搭起 80% 的骨架），然后在三维画面上手动点选剔除两个噪音节点、把某个 BICS L4 切片钉住并调整层序（方式三，精细修图），最后敲入一句简短指令「按净债务排环，只看非美供应商」（方式一，快速切视图与规则）。

1. 逐项深剖：三种交互方式的实现机理、边界与难点

1.1 方式一：简单自然语言指令（Simple Natural Language Commands）

（1）在 SFC 里的精确语义：
自然语言指令在 SFC 中绝不是「陪聊机器人」，也不是让语言直接描述三维空间里的像素位置，而是对受控图方案状态（ChartSpec）或视图状态（ViewState）发射结构化原子操作（OPS）。按照指令作用的层次，严格分为两类：

  • A 类 · 构图与映射指令（作用于后端 ChartSpec，触发 BE-BUNDLE 重算）：
    • 实体与关系编成：「以 TSMC 为中心，加入 NVDA、AAPL、AMD 作为客户，权重按营收占比」 → 编译为 SET_ANCHOR("2330 TT Equity") + ADD_PEERS([...])。
    • 切片轴（s）重排：「按 BICS 三级行业分片」「把上游设备商切片移到最前（+s）」 → 编译为 SET_S_RULE(partition="bics_l3")。
    • 面内极坐标（r, θ）切换：「环半径改按总营收排」「左右半盘改按美股与非美股划分」 → 编译为 SET_FACE_RULE(radial="ind_rev", angular="us_intl_halves")。
  • B 类 · 导航与检视指令（作用于前端 FE-ACTION / FE-SCENE，不重算布局）：
    • 「切片间距拉到 150%」「聚焦晶圆代工层并钉住」「只显示非美企业」「隐藏环导轨只看点与连线」 → 直接映射为现有 state.d = 1.5、focusSlice(i)、state.filterMode = 'intl'、state.altHideRingsSlices = true。

（2）工程实现难点与容错机制：

  • 实体指称消歧（Entity Resolution）：用户输入「台积电」「TSMC」或「Google」，而 bics_entities_20261003.db 中存储的是彭博黄键（如 2330 TT Equity、TSM US Equity、GOOGL US Equity）。目前 app.py:464 的 locate_bics(q) 已具备按 ticker 前缀与英文公司名片段检索并按 MAX(ind_rev) 排序的能力。实现自然语言指令时，必须复用 locate_bics 作为唯一实体解析器；当命中多条候选（如本股与 ADR）或中文俗称时，应在面板上弹出候选确认칩（Disambiguation Chip），而非盲目猜选。
  • 越界指令拦截（Guardrails）：若用户输入违反 CONCEPTS.md 或 AESTHETIC.md 的指令（例如「把英伟达涂成亮紫色」「画一个二维饼图」「把台积电拖到坐标 (2, 9, 1)」），编译器必须明确拒绝并提示 SFC 的标准映射规则，维护产品概念标准化。

1.2 方式二：表类数据输入（Tabular Data Input）

（1）为什么这是金融研究员最硬核、最高频的生产力底座：
DESIGN.md §3 明确规定：「数据可操作化：支持导入导出、合并拆分、添加删减，以及金融函数操作。」金融工作者的日常研究介质就是 Bloomberg Excel（BE-DATA 中的 .xlsx）、BQLX 公式表、CSV 以及研报数据表。如果让研究员在三维界面里一笔一划手敲 30 家供应链公司及其采购占比，效率极低；而允许其直接从 Excel 复制粘贴一块区域（TSV/CSV）或拖入一张表，3 秒钟就能生成一座完整的三维风险立方体。

（2）表类输入的两种标准模板与「BICS 自动富化」乘数效应：
很多系统做表格导入之所以繁琐，是因为要求用户填全所有字段（行业分类、国家、总营收、坐标等）。但在 SFC 中，因为后端坐拥 BE-BICS-ENTITY（2.8 万家公司完整主业/副业与行业营收库）和 BE-BICS-AREA（全球交易所上市地映射），用户输入的表格可以极度精简，其余 80% 的维度由后端自动左连接（Left Join）富化补齐！

表格类型用户只需提供的最小列（Minimum Columns）后端 BE-BICS-ENTITY + BE-BICS-AREA 自动补齐列编译生成的图形式

（3）与信息部（information-department）工作流的天然咬合：
当用户在制图时发现某几家公司的传导权重或债券到期数据缺失，表类输入接口可以直接导出带有缺失 ticker 列表的「待补数模板」，无缝衔接信息部 desk=request 生成 Bloomberg BQLX 公式拉取表，拉回数据后一键贴回制图台。这形成了一条完整的「制图发现缺失 → BQLX 拉数 → 贴表成图」闭环。

1.3 方式三：手动制图操作（Manual Charting Operations）

（1）核心正名：什么是「约束坐标下的手动制图」？
提到「手动制图」，外行容易联想到在 PowerPoint 或 Blender 里用鼠标把一个球随便拖到左边或上边。在 SFC 中，必须严格禁止自由拖拽篡改 (x, y) 坐标！ 原因极其深刻：在 SFC 的切片面（C-SLICE）上，点到面心的距离 r 代表该企业在该层的核心度分值（revScore ∈ [0, 100]），左半盘（x < 5）代表供应商，右半盘（x > 5）代表客户。如果允许鼠标把一个 spendPct = 1.2% 的边缘供应商直接拖到靶心 (5, 5)，几何位置就与金融事实发生了背离，整个图的信用体系当场崩塌。

因此，SFC 的手动制图操作，本质上是在三维场景与浮动玻璃面板（FE-PANEL）上，对图方案的「结构关系与映射算子」进行可视化直接操纵（Direct Structural Manipulation）：

手动操作维度具体交互手势与界面承载底层触发的 ChartSpec 原子操作（OPS）三维场景（FE-SCENE）的确定性响应
1. 节点拣选与入台
（Node Curation）		 在 FE-LIST 名单页或立方体顶栏搜索框中勾选/点击「+ 加入当前制图台」；或在立方体选中某噪音点后点击「剔除」。 ADD_NODE(ticker, role)
REMOVE_NODE(ticker)		 后端自动解析该 ticker 的 BICS L4 与营收，重算受影响切片的环分布，新节点平滑落位至对应切片与同心环。
2. 切片轴（s）编排
（Slice Manipulation）		 在面板或切片框（C-PULL-ZONE）上执行：新增一个 BICS L4 切片、合并两个相邻切片、将某切片沿 -s / +s 前后调序。 REORDER_SLICES(layerIds[])
SET_S_PARTITION(mode)		 整张切片墙带着其上的所有共面点环与连线端点，沿着 s 轴移动到新的整数层位 s = i。
3. 传导边点选搭接
（Link Authoring）		 在制图模式下，依次点选源公司环（fromId）与目标公司环（toId），在浮动小框中选择角色（supplier 墨绿 / customer 暗红）并填入权重 pct。 UPSERT_LINK(from, to, side, pct)
DELETE_LINK(from, to)		 buildRevenueLinks 立即在两点间生成双描边三维传导曲线；若当前极径规则为 link_pct，受影响节点同步沿同心环径向滑移至新分位。
4. 映射规则拨盘切换
（Mapping Rule Switch）		 在左上角或右侧浮动玻璃面板（FE-PANEL）拨动规则开关：极径指标（营收 revBn / 关联占比 linkPct / 到期债 totalBn）、极角分区（供应-客户半盘 / 美-非美半盘 / 均匀螺旋）。 SET_FACE_RULE(radial, angular, norm) 切片数不变，所有 C-POINT 根据新算出的 (ringCos, ringSin) 在各自切片面上同步重排，瞬间切换分析视角。

2. 大模型（LLM）深度裁决：有利在哪？何时会乱？为何无需重塑工程？

业主在提问中追问了两个极具战略穿透力的问题：「是否接入大模型会有利于实现？」以及「接入大模型会不会导致整个工程混乱和需要重塑？」内阁对此做出最坦率、最严密的工程裁决。

2.1 裁决一：接入大模型是否有利于实现？——「一强、一弱、一零」

不能笼统地说「大模型有用」或「没用」，必须拆开三种交互方式与两级实现梯度来看：

交互方式不接大模型（纯确定性算法）能做到什么程度？接入大模型（LLM）带来什么增量价值？内阁裁定
方式三：手动制图操作 100% 完美实现。 UI 点击 → 发射 OPS → BE-BUNDLE 重算 → FE-SCENE 渲染，全链路毫秒级响应、100% 可复现。 0% 增量价值。 手动点选与调参如果经过大模型中转，反而引入数秒延迟与不确定性。 绝对不接 LLM。 保持纯确定性状态机。
方式二：表类数据输入 90% 核心场景直接实现。 标准 CSV/TSV 或固定表头粘贴，用 100 行 Python 解析器 + locate_bics 即可瞬间完成校验与富化。 10% 辅助价值（仅限脏表清洗）。 当用户从 PDF 研报或杂乱网页复制了非标准列名、带自然语言备注的脏表时，LLM 可辅助做「列名对齐与结构化抽取建议」。 主干管线不依赖 LLM； LLM 仅可作为脏表导入前的可选预清洗助手。
方式一：简单自然语言指令 能解决 60%–70% 的受控短指令（Tier 1A：确定性 DSL / 正则槽位解析）。 例如类似 Bloomberg 命令行或快捷指令语法（anchor NVDA; add TSM supplier 37.35; ring link_pct 或固定中文句式），零延迟、零网络依赖即可跑通。 解决剩余 30%–40% 的口语化与复合意图（Tier 1B：语义意图编译）。 当用户用任意中文语序表达复合意图（如「把台积电和日月光算作英伟达上游，再把微软和 Meta 放下游，按采购和收入占比排环」）时，LLM 的 Tool-Calling / Structured Output 能极好地将其消歧并拆解为标准 OPS[] 序列。 显著有利（但仅作为「自然语言 → OPS」的前端语义编译器）。

2.2 裁决二：接入大模型会不会导致整个工程混乱和需要重塑？

答案非常明确：如果放任大模型越界，必定导致工程与金融逻辑的双重灾难；但如果用「单向窄口契约（Schema Firewall）」将大模型关进笼子，现有 26 模块 / 35 边架构连一行核心代码都无需重塑！

（A）哪两种错误接法会导致彻底混乱？（严令禁止的死路）

  1. 工程架构混乱（让 LLM 直接吐坐标或改场景代码）： 如果让大模型直接输出 Bundle JSON 里的 (s, x, y) 或 (ringCos, ringSin) 浮点数，甚至让大模型动态生成前端 JavaScript / Three.js 代码，那么 coords.js 的几何不变量、chain_layout.py 的精确半盘归一化、AESTHETIC.md 的色板约束将全部失控。每次生成的图都无法复现，regress_api_golden.py 回归测试体系将彻底报废。
  2. 金融认识论混乱（让 LLM 凭记忆编造财务数字与产业链关系）： 这是更隐蔽也更致命的风险。DESIGN.md §1 铁律写明：「可信的信息来源……无法追溯来源的数字，不算本产品的功能。」 大模型参数里记着大量过时甚至幻觉出的供应链传闻与营收数字。如果用户在制图台输入「帮我画出博通的上下游并填上采购占比」，而系统让 LLM 凭自身预训练权重胡乱编造出一串百分比画在立方体上，SFC 就会从一个严肃的金融风险决策工具堕落为「AI 幻觉玩具」。

（B）为什么只要守住三条架构铁律，现有工程「零重塑、零混乱」？

只要我们在架构上确立以下三条铁律，引入 LLM 就只是在后端挂接一个完全解耦的叶子模块（例如 BE-NL-COMPILER），对现有 26 个模块形成零冲击：

  1. 铁律一：LLM 只翻译「操作意图（OPS）」，绝不输出「几何坐标」与「无源数据」。
    LLM 的输出被严格限制在 JSON Schema 定义的有限枚举操作集内（如 {"op": "set_face_rule", "radialMetric": "ind_rev"}）。一切坐标计算仍 100% 由确定性的 Python 函数（BE-BUNDLE + BE-NVDA-LAYOUT）与前端 FE-COORDONE 执行；一切企业主业、属地、营收数据仍 100% 查自本地 SQLite 库（BE-BICS-ENTITY）或用户显式导入的表格。
  2. 铁律二：保护本地自包含应用（Standard-Financial-Charting.app）的离线独立性。
    我们在本地化改革（LOCAL-P1..P5）中刚刚实现了「内嵌 Python 3.14.8 + 本地化 Three.js + 零外部依赖、断网即开即用」的原生 macOS 应用（SHELL-WINDOW / SHELL-PROC / SHELL-PACK）。如果把云端大模型 API 写成制图台的必经脊骨，一旦断网、未配 API Key 或处于金融机构内网隔离环境，整个制图台就会瘫痪！因此，核心制图台（方式二表输入 + 方式三手动操作 + 方式一确定性快捷指令）必须 100% 离线原生可用；大模型只作为可选挂载的「自然语言口语翻译增强包（Optional Semantic Adapter）」。
  3. 铁律三：先过确认门（Confirmation Gate），再改主画布。
    当 LLM 将一句复杂自然语言编译为一组 OPS 补丁时，前端面板（FE-PANEL）可先展示为清晰可读的操作预览（例如：「即将执行：① 锚点设为 2330 TT Equity；② 新增 4 家客户节点；③ 极径切换为 revPct — [确认应用]」）。研究员一键确认后才写入图方案，彻底杜绝「模型误解一句话把辛辛苦苦搭好的图毁掉」。

4. 落地优先级排序与内阁总结建议

综合可行性、金融研究员真实痛点、以及工程稳健性，内阁给出的明确推进次序如下：

  1. 第一优先级（底座与脊骨，不接大模型）：打通 ChartSpec + 「方式二：表类数据输入」+ 「方式三：手动制图操作（规则切换与节点/连边增删）」。
    理由：这两项直接消灭「每次做图都要找代理改 Python」的痛点，且 100% 确定性、100% 离线可用、100% 符合 DESIGN.md 的数据与可视化可操作化原则。一旦表输入与 BICS 2.8 万企数据库自动左连接打通，研究员贴入一张 15 行 Excel 表就能立刻在立方体里拉出多跳传导链。
  2. 第二优先级（效率层，先做确定性快捷指令，再可选挂载 LLM）：接入「方式一：简单自然语言指令」。
    理由：当底座的 ChartSpec 与原子操作 OPS 已经稳固后，先提供一个零延迟的确定性命令栏（支持中英关键词槽位匹配）；随后若需更灵活的自然语言表达，再以 JSON Schema 约束的方式将 LLM 接入 OPS 编译口。如此，大模型成为锦上添花的加速器，而绝不会成为拖垮或搞乱工程的定时炸弹。

5. 结语与谏言状态

三种交互方式不仅全部可行，而且只要收束于同一份声明式 ChartSpec，就能与 SFC 现有的三维坐标契约、BICS 权威实体库及 macOS 本地化应用完美咬合；大模型只需严格限定在「自然语言 → ChartSpec/OPS」的编译层，绝不会引发工程混乱或推倒重塑。
