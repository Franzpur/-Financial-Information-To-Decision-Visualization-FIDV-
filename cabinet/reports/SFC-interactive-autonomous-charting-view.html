产品路径 Ind-Chain/ · 品牌字样 SFC · 姊妹篇 SFC-three-interaction-modes-and-llm-view.html · 模块真源 modules/graph.json（26 模块 / 35 边）

业主原话：「目前很多演示都是静态的，就是我把图搭好，关系搭好，让你把映射函数写好，然后展示出来看，这是很不足的，作为一个工具，他应该更多的是交互性的，自主作图的，只是格式被我们限制住，可做的图的形式被我们大大扩展，你对此有什么看法，写一个 report。」

1. 核心论断：为什么「限制格式」恰恰是「扩展图的形式」的数学前提

业主这句话点破了 Standard-Financial-Charting（SFC）从「演示沙盘」蜕变为「专业金融制图工具」的根本辩证法：格式（Format）越严格、越正交，可承载的图的形式（Forms）反而越广阔。

在可视化工程中，常见的误区是把「自主作图」等同于「无约束自由画布」（如白板工具或任意 3D 建模软件，允许用户随便摆放 (X, Y, Z)、随便改颜色与形状）。一旦放开格式，每一张图都退化为孤立的手工插画：两张图之间无法对比，相机无法保持标准视角（C-STDVIEW），切片间距 d 的拉合失去几何意义，更谈不上 DESIGN.md 所要求的「标准化」与「基于坐标的全局移动」。

反之，回顾笛卡尔平面直角坐标系或五线谱：五线谱把纵轴严格锁死在音高、横轴严格锁死在节拍，正因为谱面格式被死死限制住，它才得以脱离单首乐曲的死记硬背，通用于交响乐、赋格、爵士与室内乐。同理，SFC 已经在代码与契约层建立了一套三维金融坐标语法（Coordinate Grammar）：

约束维度代码与契约真源锁死的不变量（Format Invariants）由此解放的制图自由度（Form Expressiveness）

结论一：SFC 的三维渲染管线（FE-OPENCUBE + FE-SCENE + FE-COORDONE + FE-FOCUS）实际上已经是一台通用三维金融图渲染机。今天之所以显得「静态、单一」，绝不是因为三维格式限制太死，而是因为后端把「数据、选股、分片规则、排环规则」写死在了具体的 Python 函数里，没有把这套坐标语法的映射控制权（Mapping Sovereignty）交给运行时用户。

2. 代码级解剖：为什么当前工程困在「静态展厅样板」？

检视当前仓库的 Ind-Chain/server/bundle_dispatch.py、chain_layout.py 与 app.py，可以清晰看到「业主仓外搭关系 → 代理仓内写死映射函数 → 前端静态展示」的工程症结所在。

2.2 映射函数的「五重耦合」解剖

为什么每次业主想看一张新图，都要「我把图搭好、关系搭好，让你把映射函数写好」？因为当前在 app.py 与 chain_layout.py 中，以下五个本应正交解耦的制图算子被焊接在了一起：

  1. 实体集合算子（Entity Selection）：哪些公司进入当前立方体？目前要么是 companies.json 全集，要么是 nvda-revenue-links.json 的 peers 列表，要么是 shell 模式的单点。运行时没有「画布实体池（Active Working Set）」的概念。
  2. s 轴切片算子（Slice Partition & Ordering Rule）：在 _order_nvda_l4_slices()（app.py:622）中，分片规则被写死为「供应商主业 BICS L4（按编码升序，居 -s）→ 中心公司 BICS L4 → 客户主业 BICS L4（居 +s），若双侧共现则归入供应商侧」。如果用户想按 BICS L3 分片、按产业链自定义阶段分片、或把中心公司单独拎成一层，就必须改 Python 代码。
  3. 面内极径算子（Radial Metric & Normalization Rule）：在 db.py:135（_score_company）中极径写死读 revBn 且按层内（per-slice）min-max 归一化；而在 chain_layout.py:44 中极径写死读 linkPct 且按全局半盘（global half-disk）线性映射 radial = 0.92 - (score / 100.0) * 0.74。这两套算子本是同一极径公式的不同参数，却分裂在两个模块里。
  4. 面内极角算子（Angular Sector Rule）：在 db.py:146 中极角是黄金角/层偏置均匀撒点；在 chain_layout.py:39–41 中极角被硬编码为左半盘（supplier: [-π/2+0.28, π/2-0.28] → ringCos > 0 → x < 5）与右半盘（customer: [π/2+0.28, 3π/2-0.28] → ringCos < 0 → x > 5）。
  5. 连线生成算子（Edge / Link Rule）：在 _nvda_build_links()（app.py:831）中，连线被写死为星型拓扑（全部从 nvda_id 连向 peer_id）。若要表达多跳传导（如「台积电 → 英伟达 → 微软 → OpenAI」）或同层交叉担保，现有 builder 无法表达，尽管前端 scene.js: buildRevenueLinks 本身支持任意 fromId → toId 的点对点三维连线！

关键发现：前端 scene.js 的能力远大于后端 bundle_nvda_chain 喂给它的数据！ 前端 buildRevenueLinks 只需要 {fromId, toId, side, pct, name, country} 就能在任意两个切片（甚至同一切片）的任意两个 C-POINT 之间画出带权重的双描边曲线；前端 buildCube 只需要 layers[] 和带 (layer, ringCos, ringSin) 的 companies[] 就能渲染出任意层数的立方体。瓶颈 100% 在于后端缺少一层声明式的制图规约（ChartSpec）与通用布局编译器。

3. 在锁死的 SFC 格式下，「图的形式大大扩展」究竟能长出哪些图种？

只要我们严格守住 SFC 的格式契约（(s, x, y) 坐标、ringCos/ringSin 环投影、C-SLICE / C-POINT / C-RING / C-REV-LINK 四原语、美/非美双色环、墨绿/暗红双描边线），仅通过组合不同的 (s 轴分片算子, 极径 r 算子, 极角 θ 算子, 连线 Link 算子)，SFC 就能在不改任何前端视觉标准的前提下，从今天的 1 种图（单中心星型供应链图）直接扩展出至少 6 种服务于金融风险判断与决策（DESIGN.md §1）的标准图式：

图的形式（Chart Form）s 轴（切片层）语义面内极径 r（同心环）语义面内极角 θ（扇区/半盘）语义C-REV-LINK（有向边）语义直接服务的金融决策（对照 DESIGN.md）
形式 I：单锚点上下游传导图
（Ego Supply/Rev Chain，当前 NVDA 范式泛化至全库）		 锚点与关联方的 BICS L4（或 L3）：上游居 -s，锚点居中，下游居 +s 对锚点的采购占比 spendPct 或销售占比 revPct（占比越高越贴近圆心） 左半盘（x < 5）= 供应商；右半盘（x > 5）= 客户；锚点居圆心 (5, 5) 锚点 ↔ 上下游节点的成本/收入暴露权重 识别单一科技巨头（如 NVDA、TSM、GOOGL、ORCL）的供应链单点故障与收入集中度风险。
形式 II：多跳产业链级联图
（Multi-Hop Cascade Cube）		 按价值链传导跳数或自定义工序分层：s=0 能源/公用事业 → s=1 晶圆/设备 → s=2 算力芯片 → s=3 云厂/CSP → s=4 模型与应用 节点自身行业营收规模 ind_rev（revBn）或资本开支强度 按上市属地或法域分扇区（US 左半盘 vs INTL 右半盘，或按 BICS 子类分扇区） 跨层多跳有向边（A → B → C → D），支持任意层间与同层连线 追踪资本开支（CapEx）泡沫或断供冲击如何从终端需求逐层向晶圆与电力传导。
形式 III：债务到期墙与信用风险传导图
（Debt Maturity & Credit Contagion Cube）		 按债务到期年份桶（Maturity Wall）或信用评级档位切分：如 s=0 (2026) → s=1 (2027) → s=2 (2028) → s=3 (2029+)（直接复用并升维现有 bondSchedule 数据） 当年到期本息规模 totalBn 或净债务/EBITDA 杠杆率（到期压力越大越逼近靶心 ring=10） 左半盘 = 经营现金流可覆盖（安全区）；右半盘 = 需再融资/滚动发债（高危区） 跨期同一企业的滚续轨迹，或企业间的交叉违约、租赁承诺、应收账款敞口（如雲厂对 AI 算力租赁商的长期租约） 直击 DESIGN.md §1 核心：「风险类型上尤其注重债务风险；可视化上尤其注重以企业为节点的风险扩散与传导关系」。一眼看清哪一年、哪几家高杠杆节点构成再融资悬崖。
形式 IV：同业切片集中度与对标图
（Sub-Industry Cohort & Monopoly Stack）		 用户在 BICS 树中任选 N 个 L3/L4 细分行业并排为切片（如「晶圆代工」「半导体设备」「HBM 存储」「光模块」） 该企业在所属 L4 内的营收份额 pct_tot_rev 或绝对营收 ind_rev 按地区 listingCountry 扇区排布，保持同心环间距均匀 跨细分行业的整合并购、交叉持股或战略绑定关系（无连线时可纯看同心环分布） 通过观察各切片靶心是「单寡头独占（1 点居 ring=10，其余散落外环）」还是「群雄割据（多点密集于中环）」，瞬间判断产业链哪一环具有不可替代的定价权。
形式 V：主业与副业跨界渗透图
（Cross-Segment Penetration Cube）		 利用 bics_entities_20261003.db 中同一 ticker 的多条 entity_memberships 记录，以涉及的多个 BICS L1/L4 为切片 该企业在该切片行业的营收占比 pct_tot_rev（主业接近靶心，副业居外环） 主业节点居内环，跨界渗透节点居外侧扇区 同一法人主体在不同行业切片上的分身连线（跨层同名锚定线） 看清大型科技巨头（如 Alphabet、Microsoft、Amazon）如何在云计算、芯片自研、能源采购等多个切片同时卡位。
形式 VI：时序 / 压力情景演进图
（Temporal / Stress-Scenario Cube）		 s 轴代表时间截面或压力测试梯度：s=0 基准期 → s=1 利率 +100bp → s=2 AI 算力需求下修 30% 压力情景下的利息覆盖倍数倒数或流动性缺口评分 固定极角 θ_i（同一公司在所有 s 切片保持相同方位角，仅极径随风险恶化向靶心收缩） 连接同一公司在 s=0 → s=1 → s=2 的状态迁移轨迹线 拉动右下角间距滑块 d（从 0% 到 150%）时，直观看到哪些节点在压力下从外环安全区急速坠入中心高危区。

请看上表：这六种截然不同的专业金融分析图，没有破坏任何一条 CONCEPTS.md 的冻结约定！ 它们全部使用 (s, x, y) 摆放、全部在 [0, 10]² 的切片面上用 ringCos/ringSin 投射同心环、全部使用 C-REV-LINK 绘制传导边、全部支持 [ / ] 切层、Shift 钉住多层比对、d 滑块抽拉间距、C 键标准视角、以及 A/F 隐藏切片环导轨只看纯三维骨架。这就是业主所言「格式被我们限制住，可做的图的形式被我们大大扩展」在工程与数学上的精确落地。

4. 破局枢纽：引入声明式「图方案规约（ChartSpec）」与通用布局引擎

要从「每次让代理改 Python 写死映射函数」转向「运行时交互式自主作图」，工程上绝不是去改前端的三维渲染器，而是在后端 BE-BUNDLE 内部，把原本硬编码在 bundle_nvda_chain 里的逻辑，提炼为一份可序列化、可编辑、可校验、可保存的声明式图方案（ChartSpec），并由一个通用链/立方体编译器（Generic Layout Compiler）将其编译为现有的标准 Bundle JSON。

4.2 编译流水线：如何完美复用现有 26 模块架构？

当引入 ChartSpec 后，前后端契约与模块边界不仅不会被打乱，反而使 BE-BUNDLE、BE-DB-SHADOW、BE-NVDA-LAYOUT 的职责彻底理顺：

  1. 实体自动富化（Entity Enrichment）：ChartSpec.workingSet 里只需要给出 ticker（或通过搜索定位到的 BICS 节点），后端调 BE-BICS-ENTITY（bics_entities_20261003.db）与 BE-BICS-AREA（listing.py）自动补齐公司的标准名称、主业 L4 编码与名称、7×2 legalEntityCoord、ind_rev（自动换算 revBn）以及 US / INTL 属地。用户制图时根本不用手填这些基础金融元数据！
  2. s 轴切片编排（Slice Compiler）：根据 sAxisRule，将富化后的实体集合分配到对应的切片 layers[] 中，生成连续整数索引 idx = 0..K-1（即用户坐标 s = 0..K-1）。现有的 _order_nvda_l4_slices 只是 partitionBy = "bics_l4" + orderPolicy = "supplier_center_customer" 的一个内置策略分支。
  3. 面内 2 类坐标解算（Ring & Angle Compiler）：根据 faceRule，计算每个节点的 revScore ∈ [0, 100]、ring ∈ 0..10、radial ∈ [0, 1] 与 (ringCos, ringSin)。现有的 db.assign_rings 只是 per_slice_minmax + uniform_spiral 分支；现有的 chain_layout.assign_chain_rings 只是 global_half_disk + supplier_customer_halves 分支。
  4. 标准 Bundle 吐出：最终仍由 BE-BUNDLE 输出完全符合现有契约的 { meta, layers, companies, revenueLinks } JSON。前端 FE-API → FE-OPENCUBE → FE-SCENE → FE-COORDONE 一行几何代码都不用改，直接渲染！

4.3 让 shell 模式从「空墙死胡同」升级为「空白标准制图台」

在当前代码中，从列表点击一家未预置链文档的公司进入 /cube?ticker=TSM，触发的是 meta.mode = "shell"，画面只有 (5, 5, 5) 处孤零零的一个圆环。一旦有了 ChartSpec 架构：

  • /cube?ticker=TSM 初始打开时，实际上是加载了一份以 TSM 为中心锚点的初始空白 ChartSpec（只有 1 个中心节点）。
  • 此时它不再是一个只能按退格键退出的「死胡同」，而是一张已经架好三维坐标轴、等待用户往里添砖加瓦的制图台：用户可以一键把同属该 BICS L4 的前 10 大同业拉进来做同心环对标（即切换为形式 IV），或者导入/点选它的上下游生成传导链（即升级为形式 I/II），并把编好的图方案保存在本地用户数据目录（SFC_DATA_DIR，即 ~/Library/Application Support/Standard-Financial-Charting/）中随时复盘。

5. 交互层次的严格分野：「读图交互」与「作图交互」

为了防止后续工程实现走偏，内阁认为必须在概念上把 SFC 的交互明确划分为两层：

维度第一层：读图与空间检视交互（View / Navigation）第二层：自主作图与编成交互（Chart Authoring / Composition）
当前状态 已高度成熟（Frozen & Solid） 缺失（目前由代理在仓外写 Python 代替）
操作对象 作用于前端状态 state.js（focusLayer, pinnedLayers, selectedId, filterMode, d, 相机姿态） 作用于后端的 ChartSpec（实体增删、切片规则、极径指标、极角分区、传导连线）
具体动作 点面抽出/留驻（C-PULL）、Shift 钉住多层（C-PIN）、拉动 d 滑块（C-D）、C 键标准视角（C-STDVIEW）、搜索放大检视债券到期线（C-COMPANY-ZOOM）、A/F 开关（C-ALT） 挑入/剔除公司节点、指定锚点、切换分片依据（L4/L3/自定义阶段/期限）、切换环半径度量（营收/占比/债务）、声明/导入上下游或信用传导边、保存/加载图方案
核心铁律 绝不重算环布局（CONCEPTS.md §9.7：Server owns ring layout; browser does not re-scale rings on filter）。 绝不手搓原始坐标：任何作图操作只修改 ChartSpec，交由后端通用布局引擎重算 (s, ringCos, ringSin) 后返回标准 Bundle。

6. 演进路线图与风险防范（内阁看法，非令）

若业主决定将 SFC 从静态演示推向自主制图台，内阁建议按以下四阶秩序稳步推进（先完成模块与代码 1:1 物理对位，再进入交互化改革），避免在巨石文件上叠加交互逻辑或冲击现有稳定壳与测试金线（regress_api_golden.py）：

  1. 第零阶（交互化改革前的必经前置）：彻底完成模块与功能代码 1:1 物理对位
    • 终结 M1–M4 时「契约已立、目录未拆」的过渡妥协：将仍混居在 1,352 行 app.py 中的 BE-BICS-HIER（bics_hier.py）、BE-BICS-ENTITY（bics_entity.py）、BE-DB-SHADOW（db_shadow.py）、BE-NVDA-LINKS（nvda_links.py）彻底拆出为独立物理模块，消灭跨模块直接调用私有 _ 函数的「你中有我、我中有你」局面；前端将散落在三页的 FE-NAV 收归 nav.js，并厘清 FE-SCENE（scene.js）与 FE-FOCUS 的物理边界。
    • 此步以 100% 行为零变化（regress_all.sh full 60 项 Golden API 与打包自检零差异）为铁律，为后续 ChartSpec 编译器提供干净的模块调用底座。
  2. 第一阶：抽离通用 ChartSpec 与参数化布局引擎（后端解耦）
    • 将 bundle_nvda_chain 重构为「读取 nvda-revenue-links.json → 转换为标准 ChartSpec → 送入通用编译器 compile_chart_spec(spec)」的特例。
    • 此时 Golden API 回归测试 100% 保持字节级兼容，但后端已经具备了无需写新 Python 函数即可编译任意公司、任意分片策略、任意环指标的能力。
  3. 第二阶：打通本地持久化的图方案读写接口（SFC_DATA_DIR）
    • 利用已完成本地化的用户可写目录 SFC_DATA_DIR，支持将用户自制的 ChartSpec 保存为本地文件或 SQLite 表，使「空墙 shell」能够原地生长并保存为用户自己的命名图方案。
    • 严格遵守 W1 前后端打开权与 PUBLIC-PRIVATE.md：浏览器只通过 FE-API 发送结构化作图请求，后端独占 BE-BICS-ENTITY 与用户图方案存储。
  4. 第三阶：开放前端三大作图入口（详见姊妹篇）
    • 在 ChartSpec 底座之上，依次接入表类数据输入、手动制图操作与受约束的自然语言指令。

三条红线警告：

  • 红线一：严禁破坏 C-COORD / C-COORD-2 几何定律。 自主作图绝不允许用户在画布上把某家公司随便拖到 (x=2.1, y=8.4)——因为面内半径代表金融数值（营收或风险权重），任意拖拽等于伪造金融数据！
  • 红线二：严禁突破美学真源（AESTHETIC.md）。 无论扩展出多少种图的形式，永远只用冷暗深空底、磨砂玻璃切片、米白盘面+美/非美双色环、墨绿/暗红双描边线，绝不允许用户自定义五颜六色的节点或花哨连线。
  • 红线三：严禁无来源的自动胡画。 依据 DESIGN.md §1，「无法追溯来源的数字，不算本产品的功能」。一切进入图方案的边与权重，要么来自 BE-BICS-ENTITY / BE-DATA 权威库，要么来自研究员明确导入/录入的带源表格。

7. 结语与谏言状态

业主关于「格式限制住、图的形式大大扩展、从静态展示转向交互式自主作图」的判断，切中了 SFC 架构演进的命门。现有的三维坐标系与渲染管线正是为此而生，唯缺后端将硬编码映射解耦为声明式 ChartSpec。
